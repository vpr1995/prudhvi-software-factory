# Commands

Always run Rush through the wrapper. Do not install packages any other way.

```
node common/scripts/install-run-rush.js install      # alias: rush install
node common/scripts/install-run-rush.js build        # alias: rush build
node common/scripts/install-run-rush.js lint         # alias: rush lint
node common/scripts/install-run-rush.js typecheck    # alias: rush typecheck
node common/scripts/install-run-rush.js test         # alias: rush test
node common/scripts/install-run-rush.js verify       # alias: rush verify (runs build, lint, typecheck, test, e2e)
node common/scripts/install-run-rush.js e2e          # alias: rush e2e (Bruno and Playwright)
node common/scripts/install-run-rush.js verify --to <pkg>
node common/scripts/install-run-rush.js build --from git:origin/main
node common/scripts/install-run-rush.js verify --impacted-by git:origin/main
node common/scripts/install-run-rush.js add -p <pkg> # alias: rush add -p <pkg>
node common/scripts/install-run-rush.js new --library <name> # alias: rush new; makes packages/<name>
node common/scripts/install-run-rush.js new --project <name> # makes a bare projects/<name>
node common/scripts/install-run-rush.js add-part --project <name> --part <node|web|infra> # alias: rush add-part
node common/scripts/install-run-rush.js prettier     # alias: rush prettier
node common/scripts/install-run-rush.js audit        # alias: rush audit
node common/scripts/install-run-rush.js license-check
node common/scripts/install-run-rush.js knip         # alias: rush knip (unused files, exports, dependencies; config: knip.jsonc)
node tooling/tsconfig/scripts/check-tsconfigs.mjs     # tsconfig rules (CI runs it)
node tooling/repo-checks/scripts/doc-lint.mjs         # doc lint: links, repo paths and Rush commands in *.md (CI runs it)
node tooling/repo-checks/scripts/deploy-check.mjs     # deploy check: factory.deploy and wrangler hostnames (route, routes, env.*; custom_domain entries only, no zone_name or zone_id). CI runs it from the base commit
rush list --impacted-by git:<base> --json | node tooling/repo-checks/scripts/deploy-plan.mjs   # deploy plan: the changed projects for each deploy target. Prints four GITHUB_OUTPUT lines. `deploy.yml` runs it
node tooling/repo-checks/scripts/deploy-plan.mjs base <last-success-sha> <before-sha>   # print the commit that the deploy plan starts from
node tooling/repo-checks/scripts/test-guard.mjs "$(git merge-base main HEAD)" # test guard: weakened tests or checks in the diff (CI runs it)
node tooling/repo-checks/scripts/stop-gate.mjs defer "<reason>" # verify gate: let the main session stop without proof (logged)
node scripts/security/install-tools.mjs              # pinned gitleaks, actionlint, zizmor, pinact (rush install runs it)
bash scripts/security/workflow-lint.sh               # actionlint, zizmor, pinact on .github (hook and CI run it)
node tooling/vitest-config/dist/diff-coverage.js <base-sha> <project-path> < <project-path>/coverage/lcov.info # coverage on changed lines (CI runs it)
```

Never run `npm install`, `pnpm install`, or `pnpm add`. Use `rush add -p <pkg>` in the folder of the project.

## Notes

- Use `rush verify --to <pkg>` to check one package and its dependencies.
- `rush new --library <name>` makes a shared library from `tooling/templates/library`. It adds the `rush.json` entry and a change file, then runs `rush update`. On a bad name, it stops and writes nothing.
- `rush new --project <name>` makes a bare project from `tooling/templates/project`: the five phases, config and one test, with no parts. It adds the `rush.json` entry (no change file), then runs `rush update`.
- `rush add-part --project <name> --part <node|web|infra>` adds one part from `tooling/templates/parts/<part>` to a project that `rush new --project` made. It adds the part scripts and dependencies (versions from `projects/sample/package.json`), then runs `rush update`. It stops and writes nothing when the part exists, the project is missing, or the name is not valid.
- To check only the parts that your branch changes, run `rush build --from git:origin/main`, then `rush verify --impacted-by git:origin/main`. `--impacted-by` selects the changed projects and the projects that depend on them, but not their dependencies. `rush build --from` builds the dependencies too, so they have a `dist/` folder, also on a fresh clone.
- To run the CI checks for one project, run `rush build --to <pkg>`, then `rush lint --only <pkg>`, `rush typecheck --only <pkg>`, `rush test --only <pkg>` and `rush e2e --only <pkg>`. `.github/workflows/ci.yml` runs these commands, one job for each impacted project. `.github/workflows/warm-cache.yml` runs `rush build` for all projects on each push to `main`, so pull requests restore a full Rush build cache.
- `rush knip` runs Knip on the whole repo. It needs `tooling/vitest-config/dist`, so run `rush build --to @vprprudhvi/tooling-vitest-config` first on a fresh clone. Exit code 0 is clean, 1 is findings, 2 is an error. Fix a finding in the code. Each ignore in `knip.jsonc` needs a reason comment and a human review.
- `--only <pkg>` also selects no dependencies. Use it only when the dependencies are already built.
- Coverage on changed lines: run the tests of the project with coverage first. Exit code 0 is pass, 1 is below 80% (the lines threshold), 2 is a usage or git error. See [testing.md](../standards/testing.md) (section 2.1).
- Lint on edit (Claude Code): `.claude/settings.json` has a `PostToolUse` hook for `Edit`, `Write` and `MultiEdit`. It runs `tooling/eslint-config/scripts/lint-on-edit.mjs`. For a `.ts`, `.tsx`, `.js`, `.mjs` or `.cjs` file in a Rush project, the script runs ESLint on the file and `tsc --noEmit` on the nearest `tsconfig.json`. It skips `dist`, `.next`, `node_modules`, `coverage` and `cdk.out`. It never blocks the edit. It gives the findings to the agent as context. With no findings, it gives nothing. Each tool has a 30 s limit.
- Verify gate (Claude Code): `.claude/settings.json` runs `tooling/repo-checks/scripts/stop-gate.mjs` as a hook on `PreToolUse` (`Bash`), `PostToolUse` (edit tools and `Bash`), `PostToolUseFailure` (`Bash`), `Stop` and `SubagentStop`. Design: section 6.6.1 of [design.md](../designs/software-factory/design.md).
  - Each edit adds the file to the list of its agent. The main session uses the id `main`. The state is in `.claude/state/gate/` (gitignored).
  - Session base: the first hook call of a session stores the `HEAD` commit. A file is changed when its content differs from the session base, or when git does not track it. So a commit does not hide an edit. A file with the same content as the session base (for example after `git stash`) is unchanged.
  - Bash commands: before each command, the hook stores the sha256 of each changed source file (git status and the changes since the session base). After the command, also after a failed command, it adds each source file with a new or different hash to the list of the agent. The hook gives the change to the agent that ran the command in that time window. This is correct because writer subagents run one at a time. Two commands that run at the same time can give a file to the wrong agent. A command that runs in the background can change files after the hook checks, and the hook does not see these changes.
  - A `rush test` or `rush verify` that exits 0 stores the sha256 of each changed source file in the projects that its selectors cover (`--only`, `--to`, `--to-except`, `--from`, `--impacted-by`, `--impacted-by-except`). It gives credit only to a file with the same hash before and after the command. A file that the command changes or makes gets no credit. With no selector, it covers all projects. A selector with a tag, a git ref or `.` covers nothing. A word that looks like a selector but is not one of these forms (for example `-t=<pkg>` or `--to-version-policy`) covers nothing. The Rush command must be the last command: a pipe, `||`, `;`, `&` or `&&` after it gives no credit. A `#` at the start of a word starts a comment.
  - At a stop, the hook blocks while an edited source file (`*.ts`, `*.tsx`, `*.mts`, `*.cts`, `*.js`, `*.jsx`, `*.mjs`, `*.cjs` under `projects/`, `packages/`, `platform/` or `tooling/`) has changes and no matching hash. The message gives the command: `rush test --only <pkg>`. A source file outside each Rush project blocks too: register the project in `rush.json`. `SubagentStop` checks only the files of that subagent. `Stop` checks all files of the session. It skips unchanged and deleted files.
  - Subagent failing check: a `rush test` or `rush verify` that fails is stored for the agent, with the hashes of its unverified files. Only `;` can come before the Rush command, so a failed `cd` does not count. The subagent can then stop when that run covers all its unverified projects and the files did not change. The owner sees `Subagent stopped with failing check: <command> (projects: …)`.
  - The main `Stop` allows when each unverified file is in the edit list of a subagent that runs in the background (the task id is the agent id).
  - Deferral (main session only): run `node tooling/repo-checks/scripts/stop-gate.mjs defer "<reason>"`. The stop then shows `Verify deferred: <reason> (projects: …)` to the owner, and the hook adds a line to the deferral log in `.claude/state/`. The deferral covers only the current file content. The next change blocks again. A subagent cannot defer.
  - A hook error blocks the stop and shows the error. The agent must report it to the owner. A hook timeout (10 s) does not block: Claude Code lets the stop go on. Claude Code ends the turn after 8 blocks in a row with no tool call.
  - A `rush test` that runs in the background or that the user interrupts gives no credit.
  - State protection: `.claude/settings.json` denies `Edit(/.claude/state/**)` (the edit tools, and the targets of `sed`, `tee` and `>` in Bash) and `Bash(*.claude/state*)` (each Bash command that names the folder, also a read). It asks before an edit of `.claude/settings.local.json`. The hook commands do not go through these rules.
  - Known limit: a Bash command that writes the state without the folder name in the command text (for example a script or `cd .claude && rm -r state`) is not stopped. Such a command can forge `verified.json` or delete a block. Permission rules are not a security boundary.
  - Off switch (owner only): set `FACTORY_STOP_GATE=off` in your shell or in your user settings. Do not put it in the repo settings.
- Commit gate (Claude Code): `.claude/settings.json` runs `tooling/repo-checks/scripts/stop-gate.mjs commit` as a `PreToolUse` hook on each `Bash` command. It has no `if` filter, because the filter does not see a commit after a prefix such as `env`. It takes 0.03 to 0.04 s for a command that is not a commit. It denies `git commit` while a staged source file has no passing typecheck for its staged content. It runs no tsc and no Rush command. The pre-commit git hook runs Prettier and ESLint on staged files, so lint is not part of this gate. Design: section 6.6 of [design.md](../designs/software-factory/design.md).
  - Proof: a `rush typecheck` or `rush verify` that exits 0 stores the sha256 of each changed source file in the covered projects, in `.claude/state/gate/typechecked.json`. The rules are the same as for the test proof of the verify gate: the same selectors, Rush is the last command, and the file does not change during the run. `rush verify` runs the typecheck phase (`common/config/rush/command-line.json`), so it gives test proof and typecheck proof. `rush test` gives no typecheck proof. A `rush typecheck` gives no test proof.
  - Check: the gate reads the staged files (`git diff --cached --name-only --diff-filter=ACMR`) and keeps the source files. It uses the same source file rules as the verify gate. It hashes the staged content (the index blob), not the work tree file. Each staged source file needs a stored hash that matches. The deny message gives one command for all projects: `node common/scripts/install-run-rush.js typecheck --only <pkg> …`. A source file outside each Rush project denies: register the project in `rush.json`.
  - Partly staged file: the proof is for the work tree content, so a file with unstaged changes does not match. Stage the whole file. Or typecheck the staged content: run `git stash --keep-index`, run the typecheck, and commit. Then run `git restore --source=stash@{0} --worktree -- .` and `git stash drop` to get the unstaged changes back. Do not use `git stash pop`: it gives a merge conflict when the unstaged change is next to the staged change.
  - Allowed commit options: `-m`, `-F`, `-C`, `-c`, `-t`, `-s`, `-q`, `-v`, `-e`, `-S`, `--amend`, `--no-edit`, `--author`, `--date`, `--trailer`, `--fixup`, `--squash`, `--cleanup`, `--signoff`, `--quiet`, `--verbose`, `--allow-empty` and some more (the list is in `tooling/repo-checks/scripts/lib/commit-gate-command.mjs`). Each other option denies, also `--dry-run`. `-a`, `-i`, `-o`, `-p` and paths deny because they commit work tree content that the index does not show. Stage the files with `git add <path>`, then run `git commit -m "<message>"`.
  - Commands before the commit: the hook checks the index before the Bash command runs. So it cannot see what a command before `git commit` in the same Bash command stages. Only `cd`, `echo`, `printf`, `cat`, `true`, `pwd`, `ls`, `mkdir` and `git status`, `git diff`, `git log`, `git show` and `git rev-parse` can come before the commit. Git global options such as `--no-pager` or `-c <key>=<value>` can come before these git commands. Each other command denies (for example `git add -A && git commit`, also with `;`, a new line, or a backslash and a new line between them). A `GIT_*` variable on the commit denies too. Run `git add` in its own command, then `git commit`. Commands after the commit are not checked.
  - Commit message: the gate reads `-m "$(cat <<'EOF' … EOF)"`. It skips the body of a heredoc with a quoted delimiter (`<<'EOF'` or `<<"EOF"`), because the body is data. With an unquoted delimiter, the shell runs each command substitution in the body, so the gate does not skip it. It denies a command with `git`, then the word `commit` in the same simple command, and another command substitution or subshell (for example `cd $(mktemp -d) && git commit`), because it cannot parse it. Use `-m` (one for each paragraph) or `-F <file>`.
  - Wrapped commits: the gate skips `!`, `{`, `if`, `then`, `do`, `else`, `time`, `command`, `env`, `exec` and `nohup` before `git`. It denies a git commit in the argument text of `sh`, `bash`, `zsh`, `dash`, `eval` or `xargs`: run git commit directly.
  - The gate allows a commit with no staged source files: doc-only commits, and `git commit --amend` with nothing staged. It allows a commit in another repo (`git -C <dir>` or a `cwd` outside this repo).
  - A gate error denies the commit and shows the error text. A commit can wait until the gate works. The error never denies another command. When `node` cannot start, the hook exits 1: Claude Code shows a hook error notice and runs the command. So the commit is not checked. A hook timeout (10 s) does not deny the command either.
  - Off switch: `FACTORY_STOP_GATE=off` turns off the commit gate and the verify gate.
  - Known limits:
    - The proof is for each file, not for the full tree. A commit of some changed files of a project can have a tree that did not typecheck.
    - The gate does not check commits that `git merge`, `git cherry-pick`, `git revert`, `git am` or `git rebase --continue` make.
    - The gate does not read git aliases (for example `git ci`), and it does not see a commit in a script file (for example `bash commit.sh`).
    - The pre-commit git hook runs `prettier --write` on the staged files after the check. It can change the staged content, so the committed content can differ from the typechecked content.
    - `cd <dir> && git commit` checks this repo, also when `<dir>` is another repo.
    - A project with no `_phase:typecheck` script (for example `@vprprudhvi/tooling-repo-checks`) passes `rush typecheck` with no check, because the phase has `ignoreMissingScript`.
- Doc lint checks each tracked `*.md` file. It skips `docs/adr/`, `evals/reviewer/cases/`, `common/`, `CHANGELOG.md` files, and each design in `docs/designs/` without `status: implemented`. A design with no `status` is a finding. It fails when a relative link, a repo path in inline code, or a `rush <cmd>` names something that does not exist. It skips paths in fenced code blocks and paths with a placeholder (`<`, `>`, `*`, `{`, `}`, `$`, `...`, or a space). To skip one line, put `<!-- doc-lint-ignore-next-line -->` on the line above it.
- Deploy check scans each `projects/*/package.json`. It fails when `factory.deploy` is missing or not `cloudflare`, `aws`, `none`, or an array of `cloudflare` and `aws` with no duplicates. For a project that deploys to `cloudflare`, `wrangler.jsonc` needs a `custom_domain` route. Each such hostname must be `<label>.vprprudhvi.dev`, and no two projects may share one. The API hostname `<project>-api.vprprudhvi.dev` of an `aws` project must not equal a wrangler hostname.
- The test guard checks the committed diff from the merge base to `HEAD`. It does not check uncommitted changes. It reads the base SHA from the first argument or from `BASE_SHA`, and the PR labels from `PR_LABELS` (a JSON array). It finds the repo root from its working directory, not from its own file path. CI runs the copy of `tooling/repo-checks` from the base commit, so a change to the guard takes effect only after merge. When the base commit has no guard, CI runs the copy of the PR. A finding is one of these:
  - A deleted test file: `*.test.*`, `*.spec.*`, or a Bruno request. A rename to a test path is not a deletion. A move to a non-test name, to a `.md` path or into `test/fixtures/` is a finding.
  - Fewer `it(` or `test(` calls in a test file. Calls with modifiers count too, for example `it.each`, `it.concurrent`, `it.fails`, `it.for` and `it.skipIf(x)`.
  - An added `.skip`, `.skipIf`, `.only`, `.todo`, `.fixme`, `xit(` or `xdescribe(` in a test file, also after `.concurrent` or `.sequential`.
  - An added `eslint-disable`, `@ts-ignore`, `@ts-expect-error` or `@ts-nocheck` in any file. A line that the diff only moves in the same file is not a finding.
  - A lowered, removed or changed threshold in `tooling/vitest-config/src/config.ts` or `tooling/vitest-config/src/diff-coverage.ts`.
  - A changed check config: `eslint.config.*`, `vitest.config.*`, `playwright.config.*`, project `tsconfig*.json` (a new file of these four kinds is not a finding), `knip.jsonc`, `.lintstagedrc.cjs`, `commitlint.config.cjs`, `audit-ci.jsonc`, `tooling/tsconfig/*.json`, `common/config/rush/command-line.json`, `.github/zizmor.yml`, `.github/CODEOWNERS`, and each file in `tooling/eslint-config/`, `tooling/vitest-config/`, `tooling/repo-checks/`, `.github/workflows/` and `.github/actions/`.
  - A changed or removed script in the `scripts` of a `package.json`. A new script and a dependency change are not findings.
- The content rules skip Markdown files, `test/fixtures/` folders and `tooling/repo-checks/`. With the `risk:high` label, each finding is a warning and the exit code is 0. Without it, a finding gives exit code 1. A usage error, a bad `PR_LABELS` value, or a git or patch parse error gives exit code 2.
- Use the `verify` skill (`.claude/skills/verify/SKILL.md`) before any done claim. Use the `e2e-verify` skill (`.claude/skills/e2e-verify/SKILL.md`) for the running app.
